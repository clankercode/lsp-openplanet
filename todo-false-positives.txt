# Angelscript LSP false positives
# (LSP reports errors that the game-side compiler accepts cleanly)

## 2026-04-20, tm-draw-tests

### Case 1: Named argument resolves to wrong parameter when skipping positional args [FIXED: named args match by parameter name, skipping defaulted params]
Plugin source (src/GraphTab.as:261, 266, 271, 276):
    void AddIndentedTooltip(const string &in msg, bool pushFont = false, float w = -1.0) { ... }

    AddIndentedTooltip("...", w: 20.0);

LSP reports:
    src/GraphTab.as:261:132: error: argument 2 of `AddIndentedTooltip`: expected `bool`, got `float`

Reality:
    Game-side Angelscript compiler accepts `w: 20.0` as a named argument
    for the third parameter and compiles cleanly.

The LSP appears to be binding named arguments positionally — it maps the
named arg to the next unfilled slot (argument 2, `pushFont: bool`) instead
of matching by parameter name. Named arguments should skip over intermediate
defaulted parameters.

## 2026-08-12, tm-better-totd (LSP FPs vs game)

Remote-build on Openplanet **1.29.5**: game failed only on `Text::Join` (5×).
LSP previously reported 22 errors; after fixes → 4 empty-catch (B002) under
`#if DEPENDENCY_*` optional-dep defines.

### Fixed false positives

1. **startnew(BareFunc)** — bare function idents typed as `Named(funcName)` and
   ArgTypeMismatch vs `CoroutineFunc`. Fix: functions-as-values → `Funcdef`,
   convertible to CoroutineFunc* params.
2. **Global vars as args** (`vec4 overviewTableRowBg`, `UI::Font@ g_BoldFont`,
   `Json::Value@ meta`) — symbol extractor stored empty `type_name` for
   top-level VarDecl/Property; Ident collapsed to `Named(varName)`. Fix: lift
   type text + `lookup_global_value_type`.
3. **array.InsertLast / Find** — external overloads use unsubstituted `T`;
   ArgTypeMismatch `expected T, got LazyMap`. Fix: skip unsubstituted generic
   / `?` placeholders in external arg checks (`tostring` too).

### Not FPs / deferred

- Empty `catch {}` under optional deps: B002 true positives when defines on.
- `Text::Join`: real game error on 1.29.5; plugin targets ~1.29.12. LSP still
  silent (FN under NamespaceAccess). Version-ranged API rules: GH #18.

## 2026-08-22, tm-draw-tests (LSP FP vs game 1.29.5)

### Case: single-arg value-type constructor is not treated as an implicit conversion [FIXED 2026-08-22: GH #54, d1090f3 — typedb-driven ctor conversions; fixture 54-ctor-implicit-conversion]
Plugin source (src/DipsItem_Skel.as:112):
    mat3 rot = charRot * hatRot;
    return mat4::Translate(worldPos) * mat4::Inverse(rot);

LSP reports:
    src/DipsItem_Skel.as:112:58: error: argument 1 of `Inverse`: expected `mat4`, got `mat3`

Reality:
    Game compiles the whole plugin with zero errors — no diagnostic at all on
    DipsItem_Skel.as (file confirmed staged and compiled; no `#if` guards).

Why:
    OpenplanetCore.json registers `mat4` with a single-argument construct
    behavior `mat4(const mat3&in)` (behaviors[].type == 0, i.e.
    asBEHAVE_CONSTRUCT). AngelScript uses such single-arg value-type
    constructors as an implicit conversion when matching call arguments, so
    `mat4::Inverse(mat3)` resolves via `mat4(const mat3&in)`.
    (`mat3` symmetrically has `mat3(const mat4&in)`.)

Fix direction:
    When arg-type matching fails on an external/builtin call, allow the
    conversion if the *parameter* type is a value type in the typedb with a
    single-argument construct behavior accepting the argument type. Applies to
    every such pair in the typedb, not just mat3/mat4 (e.g. iso3/mat3,
    iso4/mat4, vec* combinations).

## 2026-08-30, B046 (FIXED) — MODULE-LEVEL engine enums

### Case: values of a namespace-level engine enum did not resolve (55 names)
Repro:
    void f() { print("" + DoubleJump); }   // also Jump, TechJump, 52 more

LSP reported:
    error: undefined identifier `DoubleJump`

Reality:
    Game compiles it (RemoteBuild probe 2026-08-30, OP 1.29.5).

Why:
    They are values of `ESceneCharVisNotice` and `ESceneVehicleVisEvent`,
    declared at MODULE level in `Openplanet.h`. The Nadeo dump's `ns` map is
    `namespace -> type name -> type`, so it can only carry an enum nested in a
    CLASS. It reaches 57 of the 59 module-level enums anyway, because a class
    member typed by one carries the enum inline (`"t": "ESpectatorCameraType"`)
    and the loader keys that `Module::EName`. These two have no such member
    anywhere in the dump, so nothing named them. Between them they carry 55
    value names that resolved nowhere; 3 of those (`DoubleJump`, `Jump`,
    `TechJump`) were resolving only by accident through the anonymous-enum
    value scan B044 narrowed, which is how the gap was noticed.

    NB the ticket's "47 module-level enums / 306 value names" was wrong; the
    header declares 59 and only 2 were missing. The "52 unresolvable" was
    right (52 + the 3 above = 55).

Fixed by:
    `src/typedb/header_format.rs` parses `Openplanet.h` for module-level
    enums; `TypeIndex::add_header` indexes only those the dump could not
    express, keyed by bare name with no namespace. `TypeIndex::load` finds the
    header beside the game dump and treats it as optional. The header now
    travels with the pair through `typedb refresh`.

Namespace attribution — settled by probe, do not re-litigate:
    The game rejects BOTH `Scene::ESceneCharVisNotice` and
    `Enums::ESceneCharVisNotice` with `Namespace '...' doesn't exist.`, and
    accepts the bare name as a type plus its values bare. `namespace Enums` in
    the header is a documentation bucket, not a namespace the game knows. So a
    module-level enum has no namespace and none is invented.

## 2026-08-30, B052 + B053 (enum resolution accuracy)

### Probe hygiene — applies to EVERY ticket in this file that says "verified against the game"
A game REJECT is evidence about the engine. A game ACCEPT may not be.

Namespaces declared by OTHER INSTALLED PLUGINS are visible to a probe compile.
`MLFeed::VirtualKey` and `VehicleState::VirtualKey` both compiled here purely
because MLFeedRaceData.op and vehicle-state-list-dev are installed; `MathX` and
`GameData` behaved the same way and were excluded from B052's model for that
reason. Discriminate with a PAIRED probe — submit `Prefix::RealName` alongside
`Prefix::ZZZNoSuchName`. `Namespace 'Prefix' doesn't exist.` for both means it
is not a scope; `Identifier 'ZZZNoSuchName' is not a data type in namespace
'Prefix' or parent` means it is, and the first result means something.

Two more traps that have each already produced a wrong number in this repo:
  * Count distinct NAMES, not index keys. The loader keys ONE engine enum under
    several modules (`Hms::EHmsLightMapQuality` and
    `MetaNotPersistent::EHmsLightMapQuality` are one enum), so `len(keys)`
    overcounts. This inflated B053's estimate 34x — 758 predicted, 22 real —
    and inflated B046's enum count before it.
  * Type lookup walks ancestor scopes; VALUE lookup does not. `UI::VirtualKey`
    compiles (the walk reaches the global enum) but `UI::GlassSmash` does not,
    though bare `GlassSmash` compiles. Never generalise a type-position result
    to value position or the reverse.

Full write-up + the committed verdict corpora (1901 qualified spellings, 2989
bare value names, with the game's verbatim message for each):
    docs/probes/README.md
    docs/probes/b052-qualified-enum-spellings.tsv
    docs/probes/b053-bare-enum-values.tsv
Regenerate with scripts/probe_enum_corpus.py (needs the game up; ONE game on
ONE port, so coordinate before running).
